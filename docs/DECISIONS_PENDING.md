# Requirement Ambiguities / Decisions Pending

The source SRS contains a few internally inconsistent statements. They are recorded here instead of being silently normalized.

## DP-001 - BN Karyalay Admin permissions

One role/permission table indicates no User/Role/Permission Management for BN Karyalay Admin, while later integrated Sections 29C / 29G describe BN Karyalay Admin as having the same administrative access as Karyalay Admin with female-specific views/analysis.

**Current implementation:** permission schema is configurable and the baseline seed follows the later integrated wording (same permissions as Super Admin). This can be changed in one seeder/matrix without schema changes if SMVS confirms the earlier table should prevail.

## DP-002 - Sanchalak context

Earlier narrative places Sanchalak in the main project hierarchy, while later page-wise/role scope material describes Sanchalak primarily under Bal Pravruti.

**Current implementation:** one configurable `sanchalak` role is seeded as a Bal Pravruti role. The security architecture supports a separate main-project Sanchalak role later if SMVS confirms they are distinct operational roles.

## DP-003 - Version labels

The cover identifies the SRS as Version 3.0 while repeating page headers refer to Version 2.0 and integrated Version 2.0 changes.

**Current implementation:** the uploaded SRS is treated as a single integrated baseline document; the latest integrated sections are not discarded. Requirement IDs in the RTM use content/page concepts instead of relying on the repeating header version.

## DP-004 - Remaining Family reporting verification

The SRS states that the remaining 4-5 Families may be selected/registered by Sankalp Karyakars and reported to Center Admin, but it does not define whether a newly reported Family becomes active immediately or requires an approval step.

**Current implementation:** selecting an already-active, eligible Family records it immediately as a `remaining` Group assignment with `assignment_source=karyakar`. Registering a brand-new Family creates a `karyakar_reported` Family in `pending_verification` plus a Remaining Family Report. An authorized Center-level user accepts or rejects that report; acceptance activates and assigns the Family subject to the same duplicate/capacity rules. This is an implementation control, not a new public-registration feature.

## DP-005 - Couple relationship evidence

The SRS requires the Couple/Husband+Wife Group type but the defined Family/Karyakar data does not provide a formal spouse-relationship key between two Karyakars.

**Current implementation:** the server validates the `couple` Group type as exactly one Male + one Female approved Karyakar and treats the authorized administrator's Group Type selection as the operational confirmation. No unsupported spouse inference is made from names or Family IDs.

## DP-006 - Target quantity versus 10-Family Group capacity

The SRS requires exactly 10 active Sankalp Families per Group, while its example scenario also describes a Group target of 100 homes/families. It does not define whether a target greater than 10 represents repeated campaign cycles, additional member-level units, or another aggregation outside the fixed 10-Family Group composition.

**Current implementation:** target quantity remains configurable and is not silently capped at 10. Phase 3 progress counts unique completed Home Visits for the active Group Family assignments within the target date/Area/Society/Karyakar scope. With one 10-Family composition, a target above 10 therefore cannot reach 100% without a separately approved interpretation/workflow change.

## DP-007 - Reminder / Alert delivery channel

The SRS requires a 4-day Reminder and 7-day Alert with status/history, but it does not specify email, SMS, push notification, WhatsApp, or another external delivery mechanism. WhatsApp automation is explicitly out of scope.

**Current implementation:** Reminder/Alert events are generated by the Laravel scheduler, retained as portal history, and displayed in the authenticated My Target and Reminders/Alerts screens. No unsupported external notification channel is added.

## DP-008 - Shared Group completion attribution

Families are assigned to a two-Karyakar Group, but the SRS does not define whether a completed Family should be credited to both Karyakars or only the person recording the Home Visit.

**Current implementation:** each Group Family assignment can be completed once. The completion counts toward Group/target progress and is attributed to the Karyakar who records the visit. Motivation badges use that individual Karyakar attribution. This avoids double-counting one Family as two completed Family visits.

## DP-009 - Inactivity clock starting point

The SRS defines the 4-day and 7-day inactivity thresholds but does not define the starting timestamp when a Karyakar has not yet recorded any visit.

**Current implementation:** for an active Group/Karyakar, the inactivity anchor is the latest Home Visit; if none exists, the later of the current active target start date and Group activation time is used; if there is no current target, Group activation time is used. No reminder/alert is generated when the Group has no pending active Family visit.

## DP-010 - Center Admin access to Bal Pravruti

The Bal Pravruti hierarchy in Integrated L1 and the integrated summary includes `Karyalay Admin -> Zone Admin -> Center Admin -> Nirdeshak -> Nirikshak -> Sanchalak`, while one Role & Permission Matrix row marks the Center Admin Bal Pravruti Module cell as `No`.

**Current implementation:** the Phase 5 seed follows the explicit Bal hierarchy/integrated summary and grants Center Admin `access_bal_pravruti`, `manage_bal_groups`, and `view_bal_analysis` within the assigned Center. Because permissions are data-driven, this can be removed without schema changes if SMVS confirms the matrix cell should prevail.

## DP-011 - Definition of a Bal Pravruti child

The Bal Pravruti section says each Group contains 3 children, but does not separately define the child's age range. Section 29B defines the Bal/Balika category as age 0-12.

**Current implementation:** Bal Group child candidates are existing active Family Members age 0-12. The portal does not create a separate unsupported child-registration universe. If SMVS defines a different Bal Pravruti age range, the eligibility guard/query can be changed without changing the Group schema.

## DP-012 - Bal contribution to overall completion percentage

The SRS explicitly says Bal Pravruti completion counts must be added to the main overall completion analysis at Zone, Center and Karyalay levels, but it does not define a Bal target/assignment denominator that could be combined with the main 10-Family Group denominator.

**Current implementation:** main analysis exposes `main completed`, `Bal completed`, and `overall completed = main + Bal`. The existing main completion percentage remains `main completed / main active assigned Families`; no unsupported combined percentage is fabricated.

## DP-013 - Nirdeshak/Nirikshak per-Group assignment cardinality

The SRS defines Nirdeshak and Nirikshak as assigned Bal Pravruti roles but does not state that every Bal Group must have exactly one Nirdeshak and exactly one Nirikshak.

**Current implementation:** an authorized Bal Group creator may assign one Nirdeshak and/or one Nirikshak at creation. These supervisor assignments define the role's visible Group scope. They are not made mandatory until SMVS confirms the operational cardinality.
